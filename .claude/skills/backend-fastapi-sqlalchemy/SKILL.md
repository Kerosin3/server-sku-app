# Бэкенд server-tracker: FastAPI + SQLAlchemy 2.0

Три слоя, границы жёсткие:

- `app/routers/` — **тонкий** слой: разобрать вход, вызвать сервис,
  отрендерить шаблон или redirect. Ни одного SQLAlchemy-запроса, ни
  одного `db.commit()`.
- `app/services/` — вся бизнес-логика и все запросы к БД.
- `app/models/` — только описание таблиц и связей.

Аудит, роли и паттерн истории компонентов — в скилле
`service-audit-crud`, здесь не дублируются. Изменения схемы — скилл
`db-migration`. Здесь — механика самих фреймворков.

## Роутер

- `templates` импортировать из `app.templating` (там фильтры `label`,
  `msk_date`, `msk_datetime`), не создавать `Jinja2Templates` локально.
- Зависимости: `db: Session = Depends(get_db)` и
  `user: User = Depends(require_role("engineer"))` — либо
  `Depends(get_current_user)`, если хватает любой аутентифицированной
  роли. Каждый роут должен иметь ровно одну из этих зависимостей;
  роут без неё открыт всем.
- Вход — `Form(...)`. UI полностью server-rendered, JSON-схем в
  `app/schemas/` пока нет. Если однажды появится JSON API — фильтрация
  полей по ролям (`customer`) переезжает туда, см. AGENTS.md.
- Успешная мутация → `RedirectResponse(url=..., status_code=303)`
  (POST/Redirect/GET: обновление страницы не повторит мутацию).
- Ошибка предметной области → поймать типизированное исключение
  сервиса и вернуть **тот же** шаблон с русским текстом `error` и
  осмысленным статусом:
  - `400` — неверный/недостаточный ввод;
  - `409` — конфликт состояния (уже занято, уже отгружено, состав
    заблокирован);
  - `404` — объекта нет.
- `raise HTTPException(...)` — только для ситуаций «при нормальной
  работе UI такого не бывает» (несуществующий id в URL, неизвестный
  `event_type` из подделанной формы). Всё, что пользователь может
  сделать штатно, показывается ему страницей с текстом, а не
  JSON-ошибкой.
- Контекст шаблона собирать одной функцией `_..._context(db, obj, user,
  error=None)` и вызывать её и на успешном пути, и на путях ошибок
  (образец — `app/routers/platform_items.py`). Иначе страница ошибки
  рано или поздно разойдётся с обычной по набору переменных и упадёт.
- Объект после мутации перечитать (`_get_item_or_404` ещё раз) перед
  рендером страницы ошибки — сессия после `commit`/`rollback` могла
  протухнуть.

## Сервис

- На каждую бизнес-ошибку — свой класс исключения с коротким
  докстрингом на английском, объясняющим **когда** оно возникает.
  Текст для пользователя живёт в роутере (он на русском), не внутри
  исключения. Единственное отступление — `PrerequisiteNotMetError`,
  который несёт `message`; не размножать этот приём.
- Одна мутация = одна транзакция:
  `db.add(...)` → `db.flush()` (если нужен id) → `audit.record(...)` →
  `db.commit()`. `audit.record` не коммитит сам — аудит обязан лечь
  той же транзакцией, что и сама мутация.
- Валидация — до записи, вся сразу, до первого `db.add`. Не оставлять
  частично применённых изменений перед тем, как бросить исключение.
- Нормализация пользовательского ввода — в сервисе, не в роутере и не
  в шаблоне (`normalize_mac`, `normalize_answer`, `.strip() or None` —
  пустая строка из формы должна становиться `None`, а не `""`).

## SQLAlchemy 2.0 — что можно и чего нельзя

- Только 2.0-стиль: `select(Model).where(...)`, `db.scalar(...)`,
  `db.scalars(...).all()`, `db.get(Model, id)`.
  Legacy `db.query(...)` не использовать. В `delete_item` и
  `delete_part_unit` он ещё остался — при правке этих функций
  переводить на `db.execute(delete(Model).where(...))`.
- Модели — `Mapped[...]` + `mapped_column(...)`, как в существующих
  файлах.
- **Жадная загрузка обязательна.** Всё, что шаблон будет обходить,
  грузить `selectinload` в сервисной функции (образец —
  `platform_items.get_item`). Ленивая подгрузка из шаблона даёт либо
  N+1 запросов, либо `DetachedInstanceError` после закрытия сессии.
  Добавили в шаблон обращение к новой связи — добавьте её в
  `selectinload`.
- **После `db.commit()` объект протухает** (`expire_on_commit` включён
  по умолчанию): следующее обращение к любому атрибуту сходит в БД, а
  если объект удалён — упадёт. Значения, нужные после коммита (пути
  файлов, id, имена), собирать **до** коммита в обычные переменные;
  если объект нужен целиком — `db.refresh(obj)` сразу после коммита.
  Готовый пример — сбор `file_paths` перед удалением в `delete_item`.
- Проверка «уже существует» на Python (`select(...) is not None`) —
  **не замена** уникальному индексу в БД. Индекс/constraint обязателен
  (он реально защищает от гонки), python-проверка нужна только для
  понятного сообщения вместо 500.
- CHECK-constraint'ы и частичные индексы (`num_nonnulls(...) = 1`,
  уникальность имени в пределах исполнения) — часть контракта модели.
  Дублировать их проверкой в Python можно ради текста ошибки, но
  убирать из БД — нельзя.

## Транзакции и целостность

- Удаление сущности с зависимостями: сначала `audit.record` (пока
  строка ещё существует и из неё можно взять данные для diff), потом
  зачистка зависимых таблиц, потом сама строка, потом один `commit`.
  Файлы с диска удалять **после** успешного коммита — иначе откат
  транзакции оставит запись в БД без файла.
- Никогда не удалять `users` физически — только `is_active=False`
  (на `users.id` ссылаются `audit_log`, `platform_events`,
  `firmware_records`). См. AGENTS.md → «Управление пользователями».

## Время

- В коде — только `datetime.now(timezone.utc)`, в БД — `TIMESTAMPTZ`.
  Наивных `datetime.now()` без таймзоны быть не должно.
- Перевод в московское время — исключительно на выводе, через
  `app/timezone.py` (фильтры в шаблонах, `format_msk_datetime` в
  экспорте). В сервисах и моделях время всегда UTC.

## Настройки и зависимости

- Новая настройка — это **три** правки: поле в `app/config.py`,
  строка в `.env.example` с комментарием, и проброс в
  `docker-compose.yml` → `environment` (иначе переменная не доедет до
  контейнера, а поле молча останется со значением по умолчанию).
- Не добавлять пакеты в `requirements.txt` без явной необходимости:
  проект должен собираться и подниматься без интернета в момент
  запуска. Версии закреплены (`==0.115.*`) — сохранять этот формат.
- Новый роутер — не забыть `include_router` в `app/main.py`, иначе
  роуты просто не существуют (никакой ошибки при этом не будет).

## Чеклист перед завершением

1. В роутере нет запросов к БД и нет `db.commit()`.
2. У каждого нового роута есть `require_role(...)` или
   `get_current_user`.
3. Каждая бизнес-ошибка ловится и показывается страницей с русским
   текстом, а не улетает 500-й.
4. Все связи, которые трогает шаблон, есть в `selectinload`.
5. Ничего не читается из ORM-объекта после `commit` без `refresh`.
6. Мутация `part_units` / `platform_items` / `platform_components`
   пишет `audit_log` (скилл `service-audit-crud`).
7. Если менялась схема — есть **новая** ревизия Alembic (скилл
   `db-migration`).
8. Если добавлялся/менялся эндпоинт `/api/v1` — обновлён каталог в
   `AGENTS.md` → «Что агент может через API», и новое сервисное
   исключение добавлено в `_ERRORS` (`app/routers/api_v1.py`), иначе
   оно улетит потребителю 500-й вместо понятного кода.
