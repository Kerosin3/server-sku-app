# server-tracker — инструкции для агента

Система учёта и трассировки серверных платформ собственного производства.
Объём: 50–300 юнитов/год. Разворачивается self-hosted (Docker Compose) на
инфраструктуре заказчика. Приоритет — надёжность и целостность данных,
не производительность под нагрузкой (нагрузка низкая).

## Общие качества агента

- Кратко, по делу — не растекаться мыслью по древу.
- Внутренние рассуждения — на английском, ответ пользователю — на
  русском (не путать с языковой конвенцией ниже — та про
  веб-интерфейс и код, а не про общение с пользователем).
- Перепроверять свои заявления перед тем, как выдавать их за факт, и
  критически относиться к входной информации (в т.ч. к словам самого
  пользователя) — не подстраивать ответ под ожидания молча.
- Не подхалимничать: указывать на проблемы и слабые места, даже если
  это значит не согласиться с пользователем.

## Языковая конвенция — НЕ НАРУШАТЬ

- **Веб-интерфейс** (всё, что рендерится в браузере: Jinja-шаблоны,
  надписи, сообщения об ошибках, которые видит пользователь) — **на
  русском языке**.
- **Всё остальное** (Python-идентификаторы, комментарии, докстринги,
  имена колонок БД, значения enum/status-кодов, CLI-скрипты,
  сообщения в логах) — **на английском языке**.
- Единая точка перевода backend-кодов в русские подписи —
  `app/i18n.py`. Любой новый код (`PlatformItem.status`,
  `PlatformEvent.event_type` и т.д.) добавляется туда же самим
  изменением, которое его вводит. Никогда не хардкодить переведённую
  строку прямо в шаблоне или роутере — искать/добавлять перевод только
  через `app/i18n.py`. Исключение — категории деталей
  (`part_categories`), это пользовательский каталог в БД, а не
  захардкоженный enum, см. «Категории деталей» ниже.
- Jinja-фильтр `label` уже зарегистрирован в `app/templating.py`
  (`{{ p.status | label('platform_status') }}`). Импортировать
  `templates` из `app.templating` во всех роутерах, не создавать
  локальные `Jinja2Templates(...)` инстансы.

## Стек (не менять без явного обсуждения)

- PostgreSQL 16 — основное хранилище
- Python 3.12 + FastAPI — backend
- SQLAlchemy 2.0 (Mapped/mapped_column style) + Alembic — ORM и миграции
- Jinja2 + HTMX + чуть-чуть Alpine.js — фронтенд. Никакого React/SPA:
  проект должен оставаться server-rendered, чтобы оставаться понятным
  человеку без опыта в вебе.
- Сессионная аутентификация (cookie), пароли — argon2
- Docker Compose: app + postgres + caddy (reverse proxy / TLS)

## Ключевой архитектурный принцип — НЕ НАРУШАТЬ

Компоненты (память, CPU, riser-карты и т.д.) никогда не привязываются к
изделию напрямую колонками вида `cpu1_serial`. Связь идёт только через
таблицу `platform_components` с полями `installed_at` / `removed_at`.
Это единственный способ:
1. поддержать переменное число компонентов одного типа на изделие
   (N планок памяти, N карт в райзере);
2. сохранить полную историю при замене компонента (RMA) —
   `removed_at IS NULL` означает "установлен сейчас", любая другая
   строка — историческая запись.

Обратный поиск "по серийнику компонента найти все изделия, где он
когда-либо стоял" — основной пользовательский сценарий. Индексы на
`part_units.serial_number` и `platform_items.asset_tag` обязательны.

### Иерархия «Платформа → Исполнение → Изделие» — НЕ НАРУШАТЬ

Три уровня, соответствующие трём разным вопросам:

- **Платформа** (`platforms`, класс `Platform`) — продуктовая линейка,
  которую разрабатывают, например «2U Storage». Только name/description,
  без деталей комплектации. Верхний уровень навигации в UI (`/platforms`).
- **Исполнение** (`platform_variants` + `platform_variant_slots`,
  классы `PlatformVariant`/`PlatformVariantSlot`) — конкретная
  BOM-конфигурация внутри платформы, например «24-bay all-flash» и
  «12-bay hybrid» под одной платформой. Это «конструктор»: эталон
  (as-planned) — какие посадочные места должно иметь изделие данного
  исполнения (CHASSIS, MOTHERBOARD, MIDPLANE, BACKPLANE_FRONT,
  BACKPLANE_REAR, IO_BOARD, USB_BOARD, PSU, CPU, DIMM, RISER_CARD, DISK
  и т.д.), с quantity и required. Задаётся один раз при заведении
  исполнения и дальше не меняется для него. У одной платформы может
  быть несколько исполнений.
- **Изделие** (`platform_items`, класс `PlatformItem`) — конкретный
  собранный физический юнит с asset tag, `platform_variant_id`
  указывает, какого он исполнения. `platform_components` — факт: что
  реально установлено сейчас/было установлено в этом изделии. Поле
  `platform_variant_slot_id` (опционально) связывает конкретную
  установку с эталонным слотом исполнения — это даёт бесплатную
  проверку комплектности (сравнить count(active) по каждому слоту с
  его quantity) без дублирования структуры вручную для каждого изделия.

Не создавать отдельные "фиксированные" колонки под platform_variants для
каждого типа платы (midplane_part_type_id и т.п.) — вся вариативность
шасси должна укладываться в строки platform_variant_slots.

UI-путь строго вложенный: `/platforms` (список платформ) →
`/platforms/{id}` (список исполнений этой платформы) → `/variants/{id}`
(конструктор слотов + список изделий этого исполнения) → `/items/{id}`
(карточка изделия: чек-лист, компоненты). Список изделий смотрят
только внутри конкретного исполнения, не через общий список всех
исполнений — так решил пользователь. Отдельно есть плоский `/`
(«Изделия») — глобальный дашборд по всем изделиям сразу с поиском по
серийнику/asset tag, для быстрого оперативного доступа в обход
иерархии.

### Категории деталей (`part_categories`) — пользовательский каталог, не enum

В отличие от всех остальных кодов в проекте (роли, статусы, типы
событий/прошивок — см. «Языковая конвенция»), категории деталей **не**
захардкожены в `app/i18n.py`. Они живут в таблице `part_categories`
(`name`, `group`) и редактируются прямо из интерфейса на
`/part-categories`, а также инлайн-формой «+ Добавить свою категорию»
на странице исполнения (`/variants/{id}`) — новую физическую форм-фактор
детали инженер заводит сам за 10 секунд, без участия агента/разработчика
и без деплоя. `name` — сразу русский текст (как `Platform.name`), без
отдельного английского кода.

Две фиксированные группы (`group`, значения `custom`/`purchased`,
подписи — `PART_CATEGORY_GROUPS` в `app/i18n.py`):
- **`purchased`** («Покупное») — готовые компоненты с рынка: PCIe/OCP
  карты, DDR, CPU, PSU, SSD M.2, диски LFF/SFF, райзер-карты.
- **`custom`** («В составе изделия») — платы собственной разработки,
  часть конструкции самого изделия: материнская плата, шасси, мидплейн,
  бэкплейн (передний/задний), IO-плата, USB-плата.

`part_types.category_id` и `platform_variant_slots.category_id` — обе
FK на `part_categories.id`, это единый список категорий и для каталога
деталей, и для слотов конструктора.

### Название и ревизия платы

`part_types.model_name` — внутреннее название модели детали,
`part_types.revision` (nullable) — её ревизия/версия. Это касается в
первую очередь плат собственной разработки (midplane, backplane_front,
backplane_rear, io_board, usb_board и подобных, в отличие от покупных
CPU/RAM/NIC, у которых модель — это готовый order code от
производителя): ревизия платы напрямую влияет на совместимость между
сборками и должна быть частью идентичности PartType, а не отдельной
пометкой в notes.

### Событийный лог изделия (вместо статичных дат)

Даты жизненного цикла конкретного собранного изделия (изготовление,
проверка/QC, первичное тестирование, финальное тестирование, отгрузка
и т.д.) хранятся не как колонки в `platform_items`, а как строки в
`platform_events` (`platform_item_id`, `event_type`, `occurred_at`,
`user_id`, `notes`). Причины:
1. новый тип события не должен требовать миграции схемы;
2. этап может повторяться (например, повторное тестирование после
   ремонта по RMA) — одна колонка-дата этого не выдержит, лог — да.

Это должно быть **интерактивным действием в UI**, а не полем ввода
даты: на карточке изделия — кнопка на каждый этап (например,
"Отметить как изготовлено"), которая проставляет `occurred_at = now()`
и текущего пользователя, а не форма для ручного ввода даты. Каждый
новый `event_type` регистрируется с русской подписью в
`app/i18n.py` (`PLATFORM_EVENT_TYPES`). Текущий набор: `manufactured`,
`qc_verified`, `initial_test`, `final_test`, `shipped`.

`platform_items.status` остаётся отдельным (денормализованным) полем
"текущий этап" для быстрой фильтрации списков — сервисный слой,
который пишет `platform_events`, обязан держать `platform_items.status`
в синхроне (например, событие `shipped` одновременно проставляет
`status="shipped"`).

### Прошивки

Таблица `firmware_records` — тот же принцип, что и `platform_events`:
append-only лог версий прошивок для `part_unit` (материнская плата:
BIOS/BMC/CPLD; бэкплейн: своя прошивка; в будущем — любая другая плата),
а не колонки `bios_version`/`bmc_version` на part_units. Причины те же:
новый тип прошивки не требует миграции, а история версий важна не
меньше текущей (для расследования отказов нужно знать, какая версия
стояла в момент выхода из строя).

`image_slot` (`primary`/`backup`) решает случай "две прошивки BIOS/BMC,
которые могут быть разных версий" (dual-BIOS/dual-BMC редундантность) —
каждый образ версионируется независимо. Для прошивок с одним образом
(CPLD, прошивка бэкплейна) `image_slot` всё равно заполняется значением
`primary` (не NULL) — так текущая версия ищется одним и тем же запросом
для всех типов, без специального случая на NULL.

Текущая версия — последняя по `recorded_at` строка для пары
`(part_unit_id, firmware_type, image_slot)` (запрос через
`DISTINCT ON` в PostgreSQL, см. докстринг модели). Каждый новый
`firmware_type` регистрируется с русской подписью в `app/i18n.py`
(`FIRMWARE_TYPES`). Текущий набор: `bios`, `bmc`, `cpld`,
`backplane_fw`.

### MAC-адреса

Таблица `mac_addresses` — MAC-адрес принадлежит либо изделию
(management/BMC-порт на уровне шасси), либо конкретному `part_unit`
(типично материнская плата: LAN1/LAN2/BMC, но в принципе любая
сетевая карта). Ровно один из `platform_item_id`/`part_unit_id`
заполнен — это гарантируется CHECK-constraint `num_nonnulls(...) = 1`
в БД, не полагаться на проверку только в Python. Не ограничивать число
MAC на владельца двумя колонками — по факту их бывает 2, но таблица
должна пережить появление 3-го интерфейса без миграции схемы.
Нормализацию формата (`AA:BB:CC:DD:EE:FF`, верхний регистр) делать в
service-слое перед записью, не полагаться на формат ввода пользователя.

## Схема данных

См. `alembic/versions/0001_initial_schema.py` — это источник истины
по схеме. Таблицы: users, part_categories, part_types, part_units,
firmware_records, platforms, platform_variants, platform_variant_slots,

audit_log (13 таблиц; platforms/platform_variants/platform_items —

## Роли и доступ

- `admin` — всё, включая управление пользователями (`/users`, см. ниже)
- `engineer` — CRUD по всей иерархии платформ (платформы/исполнения/
  изделия) и компонентов
- `viewer` — только чтение; в шаблонах для этой роли поле
  `platform_items.customer` и любые коммерческие заметки должны
  скрываться — сейчас это чисто server-rendered Jinja (не JSON API), так
  что фильтрация в шаблоне ({% if user.role != 'viewer' %}) и есть
  эквивалент "не сериализовать" — но при появлении JSON-эндпоинтов
  фильтровать нужно будет в schemas/, не полагаться на фронтенд.

Гостевой доступ = роль `viewer` с обычным логином (общий/shared
аккаунт, если нужно). Отдельного анонимного пути нет — это осознанное
решение, чтобы вся авторизация шла через один middleware.

### Управление пользователями (`app/routers/users.py`, `app/services/users.py`)

Реализовано: список, создание, смена роли, деактивация/активация,
сброс пароля. Всё — только `require_role("admin")`.

«Удаление» пользователя — это **деактивация** (`is_active=False`), не
`DELETE`-строка: на `users.id` ссылаются `firmware_records.user_id`,
`platform_events.user_id`, `audit_log.user_id` (nullable FK, без
`ON DELETE CASCADE`) — физическое удаление либо упадёт на
FK-constraint, либо (если когда-нибудь добавят `SET NULL`) молча
обезличит исторические записи о том, кто что сделал. Это прямое
применение принципа из раздела «Устойчивость к изменениям» ниже —
не частный случай, а тот же принцип.

Защита от блокировки системы: нельзя деактивировать/понизить в роли
самого себя (`SelfLockoutError`) и нельзя деактивировать/понизить
последнего активного `admin` (`LastAdminError`) — иначе некому будет
зайти и всё починить. `app/create_admin.py` остаётся нужен для
бутстрапа первого admin'а на чистой БД, где создавать пользователя
через UI ещё некому.

## Аудит

Любое создание/изменение/удаление part_units, platform_items,
platform_components, а также пользователей (создание, смена роли,
активация/деактивация, сброс пароля) должно писать запись в audit_log
(кто, что, когда, diff в JSONB). Реализовать как явный вызов
сервисного слоя (`app/services/audit.py`), не как магические
ORM-события — так проще ревьюить человеку, не являющемуся
веб-разработчиком. Platforms/platform_variants (сам каталог платформ и
исполнений) не аудируются — это справочные данные, не складской учёт.

## Устойчивость к изменениям — сохранность данных при миграциях

БД будет меняться на всём протяжении проекта (новые статусы, новые типы
событий/прошивок, новые слоты в конструкторе и т.д.) — это ожидаемый
рабочий процесс, а не исключение. При любом изменении схемы или кода,
затрагивающем существующие данные, приоритет — сохранить текущее
содержание максимально полно:

- Миграция обязана быть **сохраняющей данные** по умолчанию: `ALTER
  COLUMN` вместо `DROP` + `ADD`, `op.alter_column(..., new_column_name=)`
  вместо удаления и создания заново, backfill для новых NOT NULL
  колонок (сначала nullable + заполнение данными отдельным `UPDATE`,
  потом `NOT NULL` constraint отдельным шагом), явный маппинг старых
  enum-значений на новые при сужении списка допустимых значений (не
  просто отбрасывать те, что вышли из списка).
- Если сохранить данные при миграции в принципе невозможно (например,
  тип колонки несовместим и конвертация теряет точность) — это не
  решается молча удалением: нужно явно сообщить об этом пользователю в
  ответе и предложить план (например, перенести старое значение в
  отдельную колонку/JSONB-архив вместо того, чтобы просто его потерять).
- `downgrade()` в каждой Alembic-миграции должен быть реализован
  по-настоящему (не `pass`) и быть безопасным для существующих строк —
  даже если откат неизбежно теряет часть данных, добавленных уже после
  апгрейда, он не должен падать или портить то, что было до апгрейда.
- Прежде чем писать `DROP TABLE`/`DROP COLUMN` — проверить, не унесёт
  ли это единственную копию исторических данных. Append-only логи
  (`platform_components`, `platform_events`, `firmware_records`,
  `audit_log`) по определению самые ценные данные в системе — никогда
  не усекать и не перезаписывать их без явного запроса пользователя.
- То же касается рефакторинга кода приложения (не только схемы): не
  менять правила валидации/сериализации так, чтобы существующие записи
  в БД стали нечитаемыми или невалидными по новым правилам — либо
  писать миграцию данных под новый формат, либо явно поддерживать
  старый формат наравне с новым.
- Перед любой миграцией/изменением, способным затронуть существующие
  данные, — явно проговорить это пользователю (что теряется, что
  сохраняется, какой план) до применения, а не постфактум.

## Конвенции кода

- Бизнес-логика — в app/services/, роутеры — тонкие (валидация входа
  через Pydantic, вызов сервиса, сериализация ответа).
- Любая мутация данных — внутри одной транзакции SQLAlchemy.
- Не добавлять зависимости без необходимости — проект должен оставаться
  разворачиваемым одним `docker compose up` без интернета в момент
  запуска (только на этапе сборки образа).
- Миграции только через Alembic, руками схему в проде не трогать.
