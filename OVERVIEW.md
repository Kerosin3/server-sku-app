# Server SKU Tracker — суть и архитектура

Краткая справка для ознакомления с проектом целиком — что он решает и
как устроен. Подробности с обоснованием каждого решения — `AGENTS.md`,
развёртывание и эксплуатация — `README.md`.

---

## 1. Задача

Учёт и трассировка серверных платформ собственного производства:
50–300 юнитов в год, self-hosted, локальная сеть.

Нужно в любой момент ответить на вопросы вида:

- где сейчас стоит деталь с этим серийником и где стояла раньше;
- из чего собрано конкретное изделие и всё ли по конструктору;
- какие версии прошивок на нём записаны, какие MAC выданы;
- на каком этапе изделие и кто его туда перевёл;
- что именно уехало заказчику под этим asset tag.

Практический смысл — разбор отказов и РМА: вернувшуюся машину надо
сопоставить с тем, что в неё физически ставили полгода назад.

## 2. Стек

Python 3.12, FastAPI, SQLAlchemy 2.0, Alembic, PostgreSQL 16.
Интерфейс — Jinja2 + HTMX, без SPA. Аутентификация сессионная, argon2.
Развёртывание — Docker Compose + Caddy, одной командой.

Объём: ~7.8k строк Python, 20 сервисов, 12 роутеров, 26 шаблонов,
19 таблиц, 3 миграции.

## 3. Ключевые архитектурные решения

### 3.1. Иерархия «Платформа → Исполнение → Изделие»

Разделены *как задумано* и *как собрано*:

```
Платформа            продуктовая линейка, напр. «4U AI Server»
  └─ Исполнение      конкретная BOM-конфигурация: какие элементы,
     │               сколько, обязательные или нет + требования
     │               по прошивкам и MAC-адресам
     └─ Изделие      физический юнит с asset tag
        └─ Компоненты  что реально в нём стоит
```

Исполнение — эталон, изделие — факт. Отсюда бесплатно получается
проверка комплектности: чек-лист строится сравнением одного с другим, а
не дублированием структуры в каждое изделие руками.

### 3.2. История вместо колонок

Четыре сущности — **append-only логи**, а не поля на родительской
таблице:

| Таблица | Что хранит |
|---|---|
| `platform_components` | что стоит сейчас и что стояло раньше (`installed_at`/`removed_at`) |
| `platform_events` | вехи жизненного цикла изделия |
| `firmware_records` | версии прошивок, с учётом двух независимых образов (primary/backup) |
| `audit_log` | кто, что, когда изменил, diff в JSONB |

Снятие детали не стирает запись, а закрывает её датой. Новый тип
события или прошивки не требует миграции схемы. Полная история, а не
текущее значение, — это то, ради чего система существует.

### 3.3. Порядок этапов проверяется в границах цикла

Этапы (собрано → тест → отгружено → сервис → разобрано) идут не в
произвольном порядке: нельзя испытать несобранное, нельзя отгрузить
непроверенное.

Тонкость, которая была дефектом и исправлена: предусловия проверяются
**в текущем цикле**, а не по всей истории. Вернувшееся с объекта
изделие разбирают и собирают заново — и его старый пройденный тест
описывает машину, которой больше нет. Границу цикла задаёт событие
«разобрано». Сравнение по `id`, а не по времени: в PostgreSQL `now()` —
время транзакции, и несколько событий одной транзакции получают
одинаковую метку.

### 3.4. Два входа, один слой правил

```
     браузер                  скрипт / LLM-агент
   Jinja + HTMX                  JSON /api/v1
        │                             │
        └──────────┬──────────────────┘
                   ▼
            сервисный слой          ← все правила здесь
                   ▼
              PostgreSQL
```

Веб-роутеры и API вызывают **одни и те же сервисные функции**. Порядок
этапов, блокировка состава после укомплектования, аудит, скрытие
коммерческих полей от роли `viewer` — написаны один раз. Обойти
правило, зайдя через другой вход, невозможно, и дублировать проверки не
нужно.

### 3.5. JSON API под машинного потребителя

27 операций: 8 чтения, 19 записи — весь цикл от создания платформы до
отгрузки и удаления.

Спроектирован под LLM-агента, а не как CRUD по таблицам:

- **`dry_run` у каждой записи** — выполняются все настоящие проверки в
  настоящей транзакции, которая затем откатывается. Возвращается, что
  произошло бы. Главный предохранитель: сначала проверить, потом делать.
- **Коды и подписи разделены**: `"status": "assembled"` — контракт,
  `"status_label": "Укомплектовано"` — для человека. Переименование
  подписи не ломает потребителя.
- **Ошибки машинно-читаемые с подсказкой**, что именно исправит
  ситуацию:
  ```json
  { "error": { "code": "components_locked",
               "message": "The item is marked assembled…",
               "hint": "Record a 'disassembled' event via POST …" } }
  ```
- Удаление отказывает, пока на объект что-то ссылается, и никогда не
  трогает отгруженное изделие — это история поставленного продукта.

Доступ — по токенам из таблицы `api_tokens`. Роль у токена своя, но
никогда не выше роли его пользователя; понижение или деактивация
пользователя ограничивает все его токены автоматически. Пользователь
даёт токену личность: он пишется автором в `audit_log`, так что «кто
установил компонент» остаётся отвечаемым и когда это сделал агент.
Пока не выпущен ни один токен, API выключен.

### 3.6. LLM-агент как потребитель API

`agent/` — ассистент на LangChain: девять инструментов поверх API,
локальная модель через Ollama, переключение на внешнюю одной переменной
окружения.

Это **не третий вход в данные**, а обычный клиент: те же операции, те же
токены, те же правила. Живёт отдельно, со своими зависимостями —
приложение его не импортирует, иначе трекер перестал бы разворачиваться
одним `docker compose up`.

Модель ничего не вызывает: она читает диалог и пишет либо ответ, либо
просьбу вызвать инструмент; HTTP делает цикл на Python. Два
предохранителя намеренно живут в коде, а не в промпте, — промпт модель
может забыть:

- запись с `dry_run=false` не исполняется без явного подтверждения
  человека;
- лимит шагов и остановка на повторяющемся неверном вызове.

## 4. Сохранность данных

БД — источник истины по производству, поэтому:

- миграции обязаны сохранять данные (backfill вместо drop+add, rename
  вместо пересоздания), `downgrade()` реализован по-настоящему;
- усечение append-only логов — только с явного согласия;
- `alembic check` в скрипте развёртывания ловит расхождение моделей и
  схемы (модель поменяли, ревизию не написали) — иначе приложение
  стартует против схемы без нужной колонки;
- «удаление» пользователя — деактивация: на него ссылаются исторические
  записи о том, кто что сделал;
- бэкапы БД и загруженных файлов с ротацией, данные на bind-mount, а не
  в анонимных томах.

## 5. Тестирование

**79 тестов приложения** гоняются против настоящего приложения на
одноразовой базе: скрипт создаёт её, применяет миграции, засевает
демо-данные, потом удаляет. Мок-сервера нет намеренно — он был бы второй
реализацией того же контракта и разошёлся бы с первой.

Отдельно **контрактные тесты** фиксируют то, на что опирается
потребитель API: имена полей, набор кодов ошибок, форму конверта ошибки,
формат дат, и то, что `dry_run` действительно ничего не пишет. Там же
проверяется, что каталог эндпоинтов в документации совпадает с
реализацией, — забытое обновление документации роняет сборку.

**24 теста агента** — контракт ответа, HTTP-обёртка на подменённом
транспорте и все предохранители цикла на сценарной фейковой «модели»,
без LLM и без сервера.

Регрессионные тесты проверялись обратным способом: баг временно
возвращался, чтобы убедиться, что тест на нём падает.

## 6. Запуск

```bash
./scripts/deploy.sh     # идемпотентно: .env со случайными секретами,
                        # каталоги данных, контейнеры, миграции
```

Дальше `/setup` в браузере — первый администратор (логин, пароль,
контрольный вопрос). Вместе с ним заводится демонстрационный пример:
платформа, исполнение и укомплектованное изделие с историей, — чтобы
система открывалась заполненной, а не пустым дашбордом.

Тесты — `./scripts/test-api.sh`.

## 7. Границы

Что сознательно не сделано:

- отдельный CRUD для деталей: деталь заводится неявно, в момент
  установки на изделие;
- импорт и табличный экспорт (JSON по одному изделию есть);
- фильтры на дашборде (в API есть).

Проект учебный и до продакшена не доведён. Известные направления, в
основном по эксплуатации и безопасности, перечислены в roadmap в конце
`AGENTS.md` вместе с открытыми вопросами по правилам процесса — теми,
где решение за пользователем, а не за разработчиком.
