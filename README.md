# Server SKU Tracker

Учёт серверных платформ собственного производства: серийники шасси,
материнских плат, памяти, процессоров, карт в райзере — с полной историей
установки/замены компонентов.

Архитектура и правила разработки — см. **AGENTS.md** (обязательно к
прочтению перед тем, как вносить изменения, особенно для кодового агента).

## Запуск (self-hosted, Docker)

Быстрый путь — один скрипт, идемпотентный (безопасно запускать повторно
после `git pull`, ничего не затирает):

```bash
./scripts/deploy.sh
```

Он сам создаст `.env` со случайными `POSTGRES_PASSWORD`/`SECRET_KEY`
(если `.env` ещё нет), директории `data/postgres` и `data/uploads`,
поднимет контейнеры и применит миграции.

Вручную то же самое:

```bash
cp .env.example .env
# отредактировать .env: задать POSTGRES_PASSWORD и SECRET_KEY
#   openssl rand -hex 32   # для SECRET_KEY
# DATA_DIR/BACKUP_DIR в .env — куда на хосте лягут данные БД, загруженные
# файлы и бэкапы (bind mount, не анонимный Docker volume — так проще
# бэкапить и смотреть занятое место напрямую). По умолчанию ./data и
# ./backups рядом с проектом; в проде разумно указать абсолютный путь,
# например /srv/server-tracker/data.

docker compose up -d --build

# применить миграции
docker compose exec app alembic upgrade head

# создать первого администратора
docker compose exec app python -m app.create_admin
```

### Первый вход

После `deploy.sh` в базе нет ни одного пользователя, и приложение это
понимает: `/login` сам ведёт на **`/setup`**. Форма просит логин, пароль
(от 8 символов) и **контрольный вопрос с ответом** — последнее не
формальность, см. «Если забыли пароль» ниже.

CLI-путь для случая, когда браузера нет:

```bash
docker compose exec app python -m app.create_admin
```

**Разница между путями существенная:** `create_admin` контрольный вопрос
**не задаёт**, и созданный им администратор самостоятельно восстановить
пароль не сможет. Заведите вопрос сразу после входа: `/account/security-question`,
ссылка — своё имя пользователя в шапке.

Оба пути при создании самого первого пользователя заводят один
демонстрационный пример (платформа «DEMO 4U AI Server», исполнение
«8x GPU Full Config», изделие «DEMO-0001» с укомплектованными
компонентами, прошивками, MAC-адресами, историей этапов и файлами) —
чтобы сразу было на чём посмотреть, как выглядит заполненная система, а
не пустой дашборд. Не создаётся повторно и не трогает реальные данные:
сработает только один раз, пока в базе действительно нет ни одного
пользователя. Демо-платформу и изделие можно удалить как обычные.

Дальше остальные пользователи заводятся на `/users` (только `admin`).

### Если забыли пароль

**`/forgot-password`** — логин, затем свой контрольный вопрос, ответ и
новый пароль. Администратор для этого не нужен: в этом и смысл вопроса.
Ответ сравнивается без учёта регистра и пробелов по краям.

Ограничение: **10 неудачных попыток на логин за 15 минут** блокируют и
вход, и восстановление — счётчик у них общий, потому что неверный ответ
на контрольный вопрос это такая же попытка подобрать доступ, как и
неверный пароль.

Если вопрос не задан (администратор из `create_admin`) или пользователь
деактивирован, восстановление недоступно — форма скажет об этом, не
уточняя, какая из причин, чтобы по ней нельзя было проверять
существование логинов. Тогда остаётся сброс силами другого
администратора: `/users` → карточка пользователя → «Сбросить пароль».
Если админ в системе один и доступа к нему нет — сбрасывать пароль
командой в контейнере:

```bash
docker compose exec app python -c "
from getpass import getpass
from app.db import SessionLocal
from app.models import User
from app.services import users as users_service
db = SessionLocal()
admin = db.query(User).filter_by(username='admin').one()
users_service.reset_password(db, actor=admin, target=admin, new_password=getpass('Новый пароль: '))
print('Пароль обновлён.')
"
```

Через сервис, а не прямой записью хеша, — чтобы сброс попал в
`audit_log` наравне с остальными.

Отредактируйте `Caddyfile` — укажите реальный домен/адрес вместо
`tracker.internal.example`, либо настройте internal TLS для чисто
внутренней сети без публичного домена.

Приложение будет доступно через Caddy на портах 80/443. Для локальной
разработки без Caddy можно ходить напрямую:
`docker compose exec app uvicorn app.main:app --reload --host 0.0.0.0`

## Разработка и тесты

Тесты гоняются против **настоящего приложения на одноразовой базе** —
скрипт сам её создаёт, применяет миграции, засевает демо-пример и потом
удаляет. Рабочие данные не затрагиваются:

```bash
./scripts/test-api.sh          # весь набор
./scripts/test-api.sh -k dry_run   # одна группа
./scripts/test-api.sh -v           # подробно
```

Мок-сервера нет намеренно: он был бы второй реализацией того же
контракта и разошёлся бы с первой — с итогом «в моке всё работает, на
реальном API падает». Подробнее — в `tests/conftest.py`.

Контрактные тесты (`tests/test_api_contract.py`) фиксируют то, на что
опирается потребитель API: имена полей, набор кодов ошибок, форму
конверта ошибки, разделение кода и подписи, формат дат и то, что
`dry_run` ничего не пишет. Отдельно там же проверяется, что каталог
эндпоинтов в `AGENTS.md` совпадает с реализацией — забытое обновление
документации роняет сборку, а не тихо живёт дальше.

Зависимости для тестов — в `requirements-dev.txt`, в рабочий образ они
не попадают; скрипт ставит их в одноразовый контейнер.

Локальная разработка без Docker:

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt   # включает requirements.txt
```

## Бэкапы

БД — источник истины по производству, бэкапы обязательны. `scripts/backup.sh`
дампит БД (`pg_dump`, gzip) и архивирует загруженные файлы
(`$DATA_DIR/uploads`), затем ротирует — оставляет последние
`BACKUP_RETENTION` копий каждого (по умолчанию 10; при запуске раз в
3 дня это ~месяц истории):

```bash
./scripts/backup.sh
```

Раз в 3 дня через cron на хосте:

```cron
0 3 */3 * * cd /path/to/server-tracker && ./scripts/backup.sh >> /var/log/server-tracker-backup.log 2>&1
```

Или через systemd-таймер вместо cron — см. `scripts/systemd/README.md`
(юниты в репозитории не включены, только заготовка — накатить руками,
когда решите, что пора). Храните копии из `$BACKUP_DIR` также вне
контейнера/сервера (второй хост, S3, что угодно) — локальная копия на
том же диске не защищает от отказа диска/сервера целиком.

См. также AGENTS.md → «Где физически хранятся данные».

## JSON API (для скриптов и LLM-агентов)

Машинный интерфейс к тем же данным — `/api/v1`. Сделан под LLM-агента
(LangChain и подобные): операции под реальные вопросы, а не CRUD по
каждой таблице.

Через API проходит весь цикл — завести платформу, исполнение и его
состав, создать изделие, укомплектовать его, записать прошивки и MAC,
провести по этапам до отгрузки, поправить реквизиты, снять компонент,
удалить лишнее.

Удаление везде отказывает, пока на объект что-то ссылается, и никогда не
трогает отгруженное изделие — это история поставленного продукта. У
удаления `dry_run` передаётся в адресе (`?dry_run=true`), а не в теле:
часть HTTP-клиентов выбрасывает тело у `DELETE`, а молча пропущенный
`dry_run` на разрушающем вызове — самое неприятное, что может
произойти.

Чего через API нельзя: управлять пользователями и токенами, загружать
файлы, менять asset tag и исполнение заведённого изделия. Полный каталог
с границами и ролями — в `AGENTS.md`.

**По умолчанию выключен** — пока не выпущено ни одного токена, API
отвечает `api_disabled` и ничего не отдаёт.

### Как выпустить токен

1. Завести пользователя в интерфейсе (`/users`) — например `api`, роль
   `engineer` (или `viewer`, если API нужен только на чтение).
2. Открыть **«Токены API»** в шапке (страница `/api-tokens`, видна
   только администратору), заполнить три поля — название, от чьего имени
   действует, роль — и нажать «Создать».
3. Скопировать показанный токен. **Он показывается один раз**: в базе
   лежит только его хеш, восстановить строку нельзя. Потеряли — отзовите
   и выпустите новый.

Перезапускать приложение не нужно, токен начинает работать сразу.

То же самое из командной строки, если браузера под рукой нет:

```bash
docker compose exec app python -m app.create_api_token \
    --name "агент LangChain" --user api --role engineer

docker compose exec app python -m app.create_api_token --list
```

### Как им пользоваться

```bash
curl -H "Authorization: Bearer stk_..." \
     "http://localhost:8000/api/v1/search?q=DEMO-CPU-0001"
```

### Что означают роль и пользователь

У токена своя роль, и он привязан к пользователю. Работают обе:

- **роль токена** решает, что он может: `viewer` — только чтение и без
  коммерческих полей, `engineer` — плюс запись;
- **пользователь** даёт токену личность — он записывается автором всех
  изменений в `audit_log`, так что «кто установил этот компонент»
  остаётся отвечаемым и после того, как это сделал агент.

Роль токена никогда не бывает выше роли его пользователя. Если
пользователя понизить или деактивировать, все выданные ему токены
теряют права вместе с ним — искать и править сами токены не нужно.

Отзыв — кнопка «Отозвать» на `/api-tokens`, действует немедленно и
только на один токен: остальные потребители продолжают работать.

Схема для генерации инструментов агента — `/openapi.json`.

**Что важно знать при использовании:**

- API вызывает те же сервисы, что и веб-интерфейс, — порядок этапов,
  блокировка состава после укомплектования, ограничения на запись
  прошивок и аудит действуют одинаково. Обойти правило через API нельзя.
- У любой записи есть режим `"dry_run": true`: выполняется вся реальная
  проверка, возвращается, что произошло бы, но ничего не пишется. Для
  агента это главный предохранитель — сначала проверить, потом делать.
- Коды и подписи разделены: `"status": "assembled"` — контракт,
  `"status_label": "Укомплектовано"` — чтобы агент говорил с человеком
  по-русски. Переименование подписи в `app/i18n.py` не ломает потребителя.
- Ошибки машинно-читаемые, с подсказкой, что сделать:

  ```json
  { "error": { "code": "components_locked",
               "message": "The item is marked assembled, so its component list is locked.",
               "hint": "Record a 'disassembled' event via POST /api/v1/items/{id}/events to reopen it." } }
  ```

Токены хранятся только в виде SHA-256 — не argon2, как пароли. Пароль
человек придумывает, и его нужно защищать медленным хешем от перебора по
словарю; токен — это 256 бит от генератора случайных чисел, перебирать
там нечего, а argon2 стоил бы ~100 мс процессорного времени на **каждый**
запрос к API.

## Автозапуск при перезагрузке сервера

Заготовка systemd-юнита — `scripts/systemd/server-tracker.service`
(`docker compose up -d` при старте системы). Не установлен и не
включён — см. `scripts/systemd/README.md` для ручной установки.

## Текущий статус

**Веб-интерфейс.** Аутентификация с контрольным вопросом и
самостоятельным восстановлением пароля (`/forgot-password`,
`/account/security-question`), пользователи (`/users`, только `admin`),
токены API (`/api-tokens`, только `admin`). Иерархия Платформа
→ Исполнение → Изделие: `/platforms`, `/platforms/{id}`, `/variants/{id}`
(конструктор элементов + изделия исполнения), `/items/{id}` (чек-лист
комплектности, установка и снятие компонентов, этапы, прошивки, MAC,
файлы, выгрузка изделия в JSON); `/` — общий дашборд с поиском.
Каталоги — `/part-categories`, `/firmware-types`.

**JSON API** — `/api/v1`, 27 операций, весь цикл от создания платформы
до отгрузки и удаления, `dry_run` у каждой записи. См. раздел «JSON API»
выше.

**Агент** — `agent/`, ассистент на LangChain поверх API: девять
инструментов, работает на локальной модели через Ollama, переключается на
внешнюю одной переменной окружения. Как пользоваться —
`agent/GUIDE.md`, как устроен — `agent/README.md`.

Чего ещё нет:

- Отдельного CRUD для `part_types`/`part_units` в вебе. Деталь заводится
  неявно — в момент установки на изделие, по серийнику и артикулу.
  Отдельно есть только список бесхозных деталей (`/part-units/unowned`)
  и удаление.
- Импорта и экспорта CSV/XLSX. Выгрузка одного изделия в JSON есть —
  `GET /items/{id}/export`; табличных форматов и выгрузки пачкой нет.
- Фильтров на дашборде (в API они есть — `GET /api/v1/items`).

Открытые вопросы по правилам процесса (не дефекты, а решения, которые
за пользователем) — `AGENTS.md` → «Открытые вопросы по правилам».

Подробный статус — roadmap в конце `AGENTS.md`.
