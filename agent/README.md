# LangChain-инструменты к трекеру

Потребитель API, не часть приложения. Свои зависимости, `app/` их не
видит — трекер должен оставаться разворачиваемым одним
`docker compose up` без лишнего (см. `AGENTS.md` → «Конвенции кода»).

## Запуск

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt

# токен выпускается на /api-tokens или командой:
#   docker compose exec app python -m app.create_api_token \
#       --name "агент LangChain" --user api --role viewer
export SERVER_TRACKER_TOKEN=stk_...
export SERVER_TRACKER_URL=http://localhost:8000   # по умолчанию

.venv/bin/python demo.py
```

`demo.py` дёргает инструменты **без модели** — на успех, на доменную
ошибку, на несуществующий id. Когда агент начнёт вести себя странно,
первый вопрос всегда «а инструменты-то работают», и отвечать на него не
должно требовать ни ключа от провайдера, ни запроса наружу.

## Инструменты

| Tool | Что делает |
|---|---|
| `search_inventory(query)` | Где сейчас деталь/изделие/MAC. Точка входа: отсюда берутся id |
| `get_item(item_id)` | Полное состояние изделия: комплектность, компоненты, прошивки, MAC, этапы |
| `record_item_event(item_id, event_type, notes, dry_run)` | Отмечает этап. **По умолчанию dry run** |

Все три — обёртки над `call_api()`, одной явной HTTP-функцией. Её можно
звать напрямую, без LangChain, и именно это делает поведение проверяемым
без модели в контуре.

## Два решения, которые стоит понимать

**Ошибки возвращаются, а не бросаются.** Исключение из tool превращается
в трейсбек или в оборванный прогон, и до модели не доходит самое
полезное — `hint`, который API кладёт в каждую ошибку и который называет
вызов, исправляющий ситуацию. Поэтому и успех, и отказ приходят в одном
конверте:

```json
{"ok": true,  "status": 200, "data": {...}}
{"ok": false, "status": 409, "code": "components_locked",
 "message": "...", "hint": "Record a 'disassembled' event to reopen it."}
```

Сбой сети оформлен так же (`code: "transport_error"`), чтобы «сервер
лежит» и «ты передал неверный id» модель различала без спецразбора.

**Запись по умолчанию — сухой прогон.** `record_item_event` не пишет,
пока явно не передали `dry_run=False`. API проверяет сухой прогон ровно
теми же правилами, что и настоящий вызов — тот же сервис, та же
транзакция, только откатывается. Правильный порядок: сухой прогон →
показать человеку, что получится → повторить с `dry_run=false`. Модель,
забывшая протокол, при таком умолчании ошибается безопасно.

## Добавить инструмент

`call_api()` уже умеет весь API (27 операций, каталог — в `AGENTS.md`).
Новый tool — это функция с `@tool`, Pydantic-схемой аргументов и
докстрокой, которую **читает модель**: писать её надо как инструкцию
исполнителю, а не как комментарий для разработчика.

Осторожно с количеством: чем больше инструментов, тем хуже модель между
ними выбирает. Каталог API уже вырос до двадцати семи операций, и
переносить их в агента один-к-одному — плохая идея.
