# Агент к трекеру

Потребитель API, не часть приложения. Свои зависимости, `app/` их не
видит — трекер должен оставаться разворачиваемым одним
`docker compose up` без лишнего (`AGENTS.md` → «Конвенции кода»).

## Запуск

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt

# токен выпускается на /api-tokens или командой:
#   docker compose exec app python -m app.create_api_token \
#       --name "агент LangChain" --user api --role viewer
export SERVER_TRACKER_TOKEN=stk_...

.venv/bin/python chat.py                          # диалог
.venv/bin/python chat.py "где стоит DEMO-CPU-0001?"  # один вопрос
.venv/bin/python demo.py                          # инструменты без модели
```

## Что где

| Файл | Что внутри |
|---|---|
| `server_tracker_tools.py` | `call_api()` — явный HTTP к `/api/v1` — и три инструмента поверх него |
| `model.py` | Единственное место, знающее про провайдера. `MODEL_PROVIDER=local\|anthropic\|openai` |
| `prompt.py` | Системный промпт |
| `chat.py` | Цикл и предохранители |
| `demo.py` | Прогон инструментов без модели |

Модель ничего не вызывает сама: она пишет «хочу вызвать X с
аргументами Y», `chat.py` исполняет и кладёт результат обратно в диалог.
Весь цикл — два десятка строк.

## Переключение на внешнюю модель

```bash
pip install langchain-anthropic
export MODEL_PROVIDER=anthropic ANTHROPIC_API_KEY=...
```

Инструменты, промпт и цикл не меняются — они не знают, какая модель за
ними. Переезжает проводка; поведение нет: локальная модель ошибается
чаще, и подпорки в промпте, написанные под неё, на сильной модели
окажутся просто лишними. Поэтому отлаживать имеет смысл на слабой.

## Предохранители

Оба живут в коде, а не в промпте — промпт модель может забыть.

**Запись требует «да» от человека.** Вызов с `dry_run=false` не
исполняется, пока за клавиатурой не подтвердят. Отказали — в этом ходе
больше не спрашиваем, иначе модель, проигнорировавшая отказ, будет
дёргать человека до упора.

**Остановка на повторе.** Один и тот же вызов дважды с тем же
результатом — агент сдаётся вслух и говорит человеку, что не справился.
Лучше честный отказ, чем ход, который молча упирается в лимит шагов.

Ошибки аргументов проверяются **до** подтверждения. Наоборот было
хуже: неверный вызов отклонялся как «пользователь отказал», модель не
узнавала, что у неё неправильный тип, повторяла то же самое, и человека
спрашивали про заведомо сломанную запись снова и снова.

## Что выяснилось про локальную модель

`qwen36-claude47` (35.5B MoE, Q4_K_M) — tool calling нативный, вызов
занимает 2–4 секунды, инструменты выбирает правильно, многошаговые
цепочки (`search_inventory` → `get_item`) строит сама.

Одна находка стоит того, чтобы её знать. Поле `notes` было объявлено как
`str | None`, и модель на первой попытке заполняла его мусором —
`-2026`, `false` — а потом исправлялась на повторе. Иногда не
исправлялась вовсе. Замена на `str` с пустой строкой по умолчанию
убрала это полностью: union даёт модели два способа сказать «ничего», и
она находит третий. **В схемах инструментов union-типов лучше избегать.**

`reasoning=False` в `model.py` выключает режим размышления: на задаче
«выбери вызов и заполни поля» он ничего не добавляет.

## Добавить инструмент

`call_api()` уже покрывает весь API — 27 операций, каталог в
`AGENTS.md`. Новый инструмент это функция с `@tool`, Pydantic-схемой и
докстрокой, **которую читает модель**: писать её надо как инструкцию
исполнителю, а не как комментарий для разработчика.

Осторожно с количеством: чем больше инструментов, тем хуже модель между
ними выбирает. Переносить все 27 операций один к одному — плохая идея.
