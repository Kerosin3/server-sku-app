# Как работать с агентом

Для того, кто агента **использует**. Устройство кода и обоснование
решений — `agent/README.md`. Все примеры сняты с работающей системы.

Агент отвечает на вопросы про трекер и пишет в него — словами, без
интерфейса и без знания id. Это обычный клиент API: те же операции, тот
же токен, те же правила (порядок этапов, блокировка состава, аудит).
Обойти правило через агента нельзя — доступа к базе у него нет.

Не умеет: пользователи, токены, файлы, прошивки, MAC, смена asset tag и
исполнения.

---

## 1. Устройство

**Модель ничего не вызывает.** Она читает текст и пишет текст. Все
HTTP-вызовы делает `chat.py` — он же открывает оба соединения:

```
                 ┌──────────────┐
  вопрос  ──────▶│   chat.py    │
                 │    цикл      │
                 └──┬────────┬──┘
      «что делать?» │        │  httpx: GET/POST /api/v1/...
                    ▼        ▼  Authorization: Bearer stk_...
              ┌─────────┐  ┌──────────────┐
              │ Ollama  │  │   трекер     │
              │ qwen36  │  │ FastAPI + PG │
              │  :11434 │  │    :8000     │
              └─────────┘  └──────────────┘
```

Между Ollama и трекером стрелки нет: у модели нет сокета, она может
только сказать «вызови вот это с такими аргументами».

**Инструмент** — описание в JSON-схеме для модели плюс питоновская
функция с одним HTTP-вызовом. Их девять: шесть на чтение, три на запись
(`record_item_event`, `install_component`, `remove_component`). Список —
в `README.md`.

Шаг цикла:

1. `chat.py` шлёт модели системный промпт + всю историю + девять схем.
2. Модель отвечает текстом (ход закончен) или просьбой вызвать инструмент.
3. `chat.py` проверяет аргументы, при записи спрашивает человека, зовёт API.
4. Результат дописывается в историю, и **всё уходит модели заново,
   целиком** — своей памяти у неё нет.
5. До ответа текстом, максимум 12 шагов.

## 2. Установка

```bash
./scripts/deploy.sh              # трекер на :8000
ollama list                      # модель на :11434

cd agent
python -m venv .venv && .venv/bin/pip install -r requirements.txt
```

Дальше токен — без него `call_api()` не пойдёт в сеть, а вернёт
`no_token_configured`. Сам API тоже выключен, пока не выпущен первый
токен: всем отвечает `api_disabled`.

### Пользователь

Токен привязан к пользователю, и этот пользователь пишется автором в
`audit_log` — «кто установил компонент» должно оставаться отвечаемым и
когда это сделал агент. Поэтому **отдельная учётка**, не твоя: видно, где
работал агент, и отключается он одной кнопкой «Деактивировать» разом со
всеми своими токенами.

`/users` (только админ) → создать: логин `api`, роль Инженер, пароль
любой от 8 символов — агент им не пользуется.

### Токен

`/api-tokens` (только админ), три поля:

| Поле | Значение |
|---|---|
| Название | `агент LangChain` — по нему потом отзывать |
| Действует от имени | `api` |
| Роль токена | `engineer` для записи, `viewer` только для чтения |

**Токен показывается один раз** — в базе только SHA-256. Потерял →
отзывай и выпускай новый.

То же из командной строки:

```bash
docker compose exec app python -m app.create_api_token \
    --name "агент LangChain" --user api --role engineer

docker compose exec app python -m app.create_api_token --list
```

```
name                         prefix         role       acts as          status
агент LangChain              stk_eVgNtN95…  engineer   api              active
полная проверка              stk_YuSJcZCB…  admin      admin            revoked
```

Без флагов спросит те же поля интерактивно. Пользователя не создаёт.

### Отдать агенту

```bash
export SERVER_TRACKER_TOKEN=stk_...

# проверить без агента:
curl -H "Authorization: Bearer $SERVER_TRACKER_TOKEN" \
     "http://localhost:8000/api/v1/search?q=DEMO"
```

Перезапускать ничего не нужно, токен работает сразу.

### Роли

| Роль | Что может агент |
|---|---|
| `viewer` | чтение, **без коммерческих полей** — заказчика не увидит |
| `engineer` | плюс запись: этапы, установка и снятие компонентов |
| `admin` | для агента то же, что `engineer` — его две лишние операции ни одним инструментом не покрыты |

По умолчанию `engineer`. Если агент нужен только отвечать на вопросы,
бери `viewer`: тогда записать он не сможет вообще, независимо от
предохранителей.

**Роль токена никогда не выше роли его пользователя** — проверяется и
при выпуске, и на каждом запросе. Понизил пользователя — токены урезались
в ту же секунду, деактивировал — перестали работать совсем
(`service_account_disabled`). Отзыв одного токена — кнопка «Отозвать»,
остальные продолжают работать; отзыв последнего живого выключает API.

## 3. Запуск

```bash
.venv/bin/python chat.py                             # диалог
.venv/bin/python chat.py "где стоит DEMO-CPU-0001?"  # один вопрос
.venv/bin/python demo.py                             # инструменты без модели
```

Пустая строка или Ctrl-D — выход.

`demo.py` прогоняет инструменты **без модели**. Когда агент ведёт себя
странно, первый вопрос — «а инструменты работают?», и отвечать на него
не должно требовать LLM.

## 4. Примеры

Строки `→` — трасса: что модель попросила вызвать и чем это кончилось.
Печатается по ходу.

**Один вызов:**

```
> где стоит DEMO-CPU-0001?
  → search_inventory({"query": "DEMO-CPU-0001"})
    success

Status: success
Action: search_inventory [success]
Data: DEMO-CPU-0001 (Xeon Gold 6448Y) сейчас установлен в изделие DEMO-0001 (id=1).
```

**Цепочка** — id знать не нужно, модель находит его сама:

```
> изделие DEMO-0001 полностью укомплектовано?
  → search_inventory({"query": "DEMO-0001"})
    success
  → get_item({"item_id": 1})
    success

Status: success
Action: search_inventory [success] → get_item [success]
Data: Да, полностью: CPU 2/2, DDR 8/8, PSU 2/2 … Опциональные (OCP карта,
задний бэкплейн) не установлены — это нормально. Состояние: Отгружен.
```

`search_inventory` — точка входа, отсюда берутся id.

**Запись — в два приёма.** Сначала сухой прогон (по умолчанию):

```
> отметь на DEMO-0001 сервисное обслуживание, замена вентилятора
  → search_inventory({"query": "DEMO-0001"})
    success
  → record_item_event({"item_id": 1, "event_type": "service", "notes": "замена вентилятора"})
    success

Status: success
Data: Проверка прошла успешно. Сервисное обслуживание с комментарием
«замена вентилятора» можно записать на DEMO-0001 (id=1). Подтверждаете?
```

Сухой прогон не заглушка: трекер выполняет все настоящие проверки в
настоящей транзакции и откатывает её. Отказ по правилу процесса придёт
здесь, до записи.

Соглашаешься — агент останавливается **ещё раз**:

```
> да
  → record_item_event({..., "dry_run": false})

  ⚠ Модель хочет записать в базу: record_item_event({"item_id": 1, "event_type": "service", "notes": "замена вентилятора"})
    Выполнить? [y/N] n
    error — refused_by_user

Status: success
Action: record_item_event [error — refused_by_user]
Data: Запись отменена — пользователь не подтвердил. Ничего не записано.
Errors: record_item_event: refused_by_user
```

Два вопроса — не дублирование. Первый задала модель: её можно уговорить
или она забудет спросить. Второй задал код, который выполняет вызов, —
его не обойти формулировкой. **Без явного `y` в этой строке в трекер не
уходит ни одна запись.** Ответил `n` — в этом ходе больше не спросят.

## 5. Как читать ответ

```
Status: success | error
Action: <цепочка вызовов с исходом каждого>
Data:   <ответ>
Errors: <код: сообщение + подсказка>
```

- `Status` — про **ход**, а не про вызовы внутри. `success` при
  отказанной записи не опечатка: агент сделал своё дело и сказал, что
  записи не было.
- `Errors` заполняется и при `success`, если по дороге что-то падало —
  «ответил, но после трёх отклонённых вызовов» иначе не видно.

**Сверяй `Data` с `Action`.** Модель — единственное звено, которое может
соврать; трасса не может. В `Data` «записал», а в `Action` нет успешного
вызова — верна трасса.

## 6. Если что-то не работает

Первые пять — про токен, лечатся разделом 2.

| Код | Что значит |
|---|---|
| `no_token_configured` | не задан `SERVER_TRACKER_TOKEN` — запрос не отправлялся |
| `api_disabled` | нет ни одного живого токена; выпустить на `/api-tokens` |
| `unauthenticated` | токен неверный или отозван; восстановить нельзя, выпускай новый |
| `forbidden` | роль не позволяет: `viewer` там, где нужна запись, — или пользователя токена понизили |
| `service_account_disabled` | пользователя токена деактивировали; включить в `/users` |
| `transport_error` | трекер не отвечает: не поднят или `SERVER_TRACKER_URL` не тот |
| `prerequisite_not_met` | этап нельзя записать в этом порядке. Не поломка, а отказ по существу — в сообщении сказано, чего не хватает |
| `components_locked` | изделие укомплектовано, состав закрыт; открыть событием `disassembled` |
| `invalid_arguments` | модель передала не тот тип; обычно исправляется сама |
| `repeated_call` | модель повторяет один и тот же неверный вызов и сдалась вслух — переформулируй или сделай в вебе |
| `step_limit` | 12 шагов без ответа, скорее всего зациклилась |

**Инструменты или модель?** Запусти `demo.py` — он ходит в трекер теми же
функциями без LLM. Работает → дело в модели или формулировке; нет → в
токене, адресе или трекере.

**Длинный разговор начал путаться.** История не подрезается, в контекст
32768 несколько `get_item` вытесняют начало. Перезапусти `chat.py`.

## 7. Что спрашивать

Ложится хорошо: где стоит деталь и где стояла раньше; что с изделием и
всё ли укомплектовано; что в тестировании, сколько отгружено; что должно
быть по конструктору; отметить этап, поставить и снять деталь.

Замена детали работает, но подтверждать будешь **дважды** — снятие и
установку. Серийник новой детали называй сразу, иначе агент переспросит
(и правильно сделает).

Ложится плохо: чего нет среди девяти инструментов (пользователи, токены,
файлы, прошивки, MAC — в API есть, инструментов нет); массовые операции
(12 шагов); аналитика по всей базе — SQL агент не выполняет.

По одному действию за раз. «Проверь и, если всё хорошо, отгрузи» модель
выполнит, но подтверждать будешь вслепую.

## 8. Внешняя модель

```bash
.venv/bin/pip install langchain-anthropic
export MODEL_PROVIDER=anthropic ANTHROPIC_API_KEY=...
```

Меняется только левая стрелка на схеме: про провайдера знает единственный
файл `model.py`. Переезжает проводка, не поведение — локальная модель
ошибается чаще, поэтому отлаживать разумно на ней.
