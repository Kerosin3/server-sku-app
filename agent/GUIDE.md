# Как работать с агентом

Инструкция для того, кто агента **использует**. Про устройство кода и
про то, почему решения приняты именно такие, — `agent/README.md`;
каталог API и правила процесса — `AGENTS.md`.

Все примеры ниже сняты с работающей системы, а не написаны от руки.

---

## 1. Что это такое

Ассистент, который отвечает на вопросы про трекер и записывает в него
этапы — обычными словами, без интерфейса и без знания id.

Это **обычный клиент API**, такой же, как браузер. Он ходит теми же
двадцатью семью операциями, с тем же токеном, и упирается в те же
правила: порядок этапов, блокировку состава после укомплектования,
аудит. Обойти правило через агента нельзя — он не имеет доступа к базе
и вообще не знает, что она существует.

Чего он не делает: не управляет пользователями и токенами, не загружает
файлы, не меняет asset tag и исполнение заведённого изделия.

---

## 2. Устройство

Главное, что стоит понять сразу: **модель ничего не вызывает**. Ни
трекер, ни базу, ни HTTP. Она умеет только читать текст и писать текст.

Участников четыре, и по сети идут два независимых соединения — оба
открывает `chat.py`:

```
                 ┌──────────────┐
  вопрос  ──────▶│   chat.py    │
                 │    цикл      │
                 └──┬────────┬──┘
      «что делать?» │        │  httpx: GET/POST /api/v1/...
                    ▼        ▼  Authorization: Bearer stk_...
              ┌─────────┐  ┌──────────────┐
              │ Ollama  │  │   трекер     │
              │ qwen36  │  │ FastAPI + PG │
              │  :11434 │  │    :8000     │
              └─────────┘  └──────────────┘
```

| Кто | Где | Что делает |
|---|---|---|
| человек | терминал | задаёт вопрос, подтверждает записи |
| `chat.py` | python-процесс, `agent/.venv` | цикл: спрашивает модель → исполняет то, что она попросила |
| модель | Ollama, 21 ГБ весов | получает текст, возвращает текст или просьбу вызвать инструмент |
| трекер | Docker, `/api/v1` | те же сервисы, что и веб-интерфейс |

Между Ollama и трекером стрелки нет. У модели нет сокета; всё, что она
может, — сказать «вызови вот это с такими аргументами», а исполняет это
питоновский код.

**Инструмент** — это две вещи сразу. Для модели: описание в JSON-схеме
(имя, назначение, аргументы с типами), которое подмешивается **в каждый
запрос** к Ollama. Для питона: функция, внутри которой один явный
HTTP-вызов. Инструментов девять: шесть на чтение, три на запись. Полный
список — в `README.md`.

### Один шаг цикла

1. `chat.py` отправляет модели: системный промпт + всю историю диалога +
   девять схем инструментов.
2. Модель отвечает либо текстом (ход закончен), либо просьбой вызвать
   инструмент.
3. `chat.py` проверяет аргументы, при записи спрашивает человека,
   выполняет HTTP-вызов.
4. Результат дописывается в историю, и **всё отправляется модели
   заново, целиком**. Своей памяти у модели нет — история диалога это
   буквально список сообщений в питоне.
5. Повторять, пока модель не ответит текстом. Максимум 12 шагов.

**Трекер и Ollama должны быть подняты:**

```bash
./scripts/deploy.sh              # трекер на :8000
```

**Окружение агента:**

```bash
cd agent
python -m venv .venv && .venv/bin/pip install -r requirements.txt
```

## 4. Токен

Без токена агент не работает вообще: `call_api()` даже не пойдёт в сеть,
а вернёт `no_token_configured`. И сам API по умолчанию **выключен** —
пока не выпущено ни одного токена, он отвечает `api_disabled` всем.

Выпуск — в два шага: сначала пользователь, потом токен от его имени.

### Шаг 1. Пользователь, от чьего имени работает агент

Токен привязан к пользователю, и это не формальность: именно этот
пользователь записывается автором всех изменений в `audit_log`. Вопрос
«кто установил этот компонент» должен оставаться отвечаемым и после
того, как это сделал агент.

Заводить **отдельного** пользователя, а не выдавать токен от себя. Тогда
в истории видно, где работал агент, а где человек, — и отключается он
одной кнопкой «Деактивировать» на карточке этого пользователя, разом со
всеми его токенами.

Интерфейс → **«Пользователи»** (`/users`, видна только администратору) →
создать, например:

| Поле | Значение |
|---|---|
| Логин | `api` |
| Пароль | любой, от 8 символов — форма требует, агент им не пользуется |
| Роль | Инженер |

### Шаг 2. Токен

Интерфейс → **«Токены API»** в шапке (`/api-tokens`, тоже только
администратор). Три поля:

| Поле | Что писать |
|---|---|
| Название | Зачем этот токен — `агент LangChain`. Оно попадёт в список, по нему потом отзывать |
| Действует от имени | `api` — пользователь из шага 1 |
| Роль токена | `engineer` для записи, `viewer` если агенту нужно только чтение |

Нажать «Создать». Токен появится в баннере на этой же странице.

**Скопировать его сразу.** Показывается он ровно один раз: в базе лежит
только SHA-256-хеш, восстановить строку нельзя ни через интерфейс, ни
через базу. Потерял — отзывай и выпускай новый, других вариантов нет.

### То же самое из командной строки

Если браузера под рукой нет — например, первичная настройка на сервере:

```bash
docker compose exec app python -m app.create_api_token \
    --name "агент LangChain" --user api --role engineer
```

```
Token 'агент LangChain' created — role engineer, acting as api.
Copy it now; it is not stored and cannot be shown again:

    stk_...
```

Без флагов команда спросит те же три поля интерактивно. Пользователя она
не создаёт — если его нет, скажет об этом и остановится.

Посмотреть, что уже выпущено (секретов там нет, только префиксы):

```bash
docker compose exec app python -m app.create_api_token --list
```

```
name                         prefix         role       acts as          status
агент LangChain              stk_eVgNtN95…  engineer   api              active
полная проверка              stk_YuSJcZCB…  admin      admin            revoked
```

### Отдать токен агенту

```bash
export SERVER_TRACKER_TOKEN=stk_...
```

Переменная нужна в том же окружении, где запускается `chat.py`. Ничего
перезапускать не надо — ни трекер, ни агента: токен начинает работать
сразу после создания.

Проверить, что он живой, можно и без агента:

```bash
curl -H "Authorization: Bearer $SERVER_TRACKER_TOKEN" \
     "http://localhost:8000/api/v1/search?q=DEMO"
```

Или через `demo.py` — он прогонит инструменты по-настоящему.

### Какая роль нужна

| Роль | Что может агент |
|---|---|
| `viewer` | только чтение, и **без коммерческих полей** — заказчик в выдаче не появится |
| `engineer` | плюс запись: этапы, установка и снятие компонентов |
| `admin` | плюс удаление платформы и исполнения — но ни один инструмент агента этого не делает |

Разумное значение по умолчанию — `engineer`. Если агент нужен только
чтобы отвечать на вопросы, бери `viewer`: тогда никакая ошибка модели и
никакая неудачная формулировка не смогут ничего записать, независимо от
предохранителей.

`admin` этому агенту брать незачем. В API за ним закреплены ровно две
операции — удаление исполнения и удаление платформы, — и обе не покрыты
инструментами, так что для агента такой токен ничем не отличается от
`engineer`. Пользователями и токенами через API не управляют вообще, ни
под какой ролью.

### Как токен ограничен

**Роль токена никогда не выше роли его пользователя.** Проверяется
дважды: при выпуске (`engineer`-токен на `viewer`-пользователя выдать не
дадут) и на каждом запросе — права считаются как минимум из двух ролей.

Практический смысл: понизил пользователя — его токены урезались до его
новой роли в ту же секунду; деактивировал — они перестали работать
совсем (`service_account_disabled`). Искать и править сами токены не
нужно, и забыть про какой-нибудь из них невозможно.

**Отзыв** — кнопка «Отозвать» на `/api-tokens`. Действует немедленно и
только на один токен: остальные потребители продолжают работать.

Отзывать стоит не только при утечке — токен, который больше не нужен,
это лишний живой доступ. И помни, что отзыв последнего живого токена
выключает API целиком: он снова начнёт отвечать `api_disabled`.

## 5. Запуск

```bash
.venv/bin/python chat.py                             # диалог
.venv/bin/python chat.py "где стоит DEMO-CPU-0001?"  # один вопрос и выход
.venv/bin/python demo.py                             # инструменты без модели
```

Пустая строка или Ctrl-D — выход.

`demo.py` стоит запомнить: он прогоняет инструменты **без модели**.
Когда агент ведёт себя странно, первый вопрос — «а инструменты-то
работают?», и отвечать на него не должно требовать LLM.

## 6. Пример: простой вопрос

```
> где стоит DEMO-CPU-0001?
  → search_inventory({"query": "DEMO-CPU-0001"})
    success

Status: success
Action: search_inventory [success]
Data: DEMO-CPU-0001 (Xeon Gold 6448Y) сейчас установлен в изделие **DEMO-0001** (id=1).
```

Строки со стрелкой `→` — это трасса: что модель попросила вызвать и чем
это кончилось. Она печатается по ходу дела, чтобы было видно, чем агент
занят, а не только итог.

## 7. Пример: цепочка вызовов

Id знать не нужно — модель находит его сама и идёт дальше:

```
> изделие DEMO-0001 полностью укомплектовано?
  → search_inventory({"query": "DEMO-0001"})
    success
  → get_item({"item_id": 1})
    success

Status: success
Action: search_inventory [success] → get_item [success]
Data: Да, изделие DEMO-0001 полностью укомплектовано. Все обязательные
компоненты установлены:

| Компонент | Требуется | Установлено |
|-----------|-----------|-------------|
| CPU | 2 | 2 |
| DDR | 8 | 8 |
| PSU | 2 | 2 |
…
Опциональные компоненты (OCP карта, задний бэкплейн) не установлены —
это нормально.

Состояние: **Отгружен**.
```

`search_inventory` — обычная точка входа: отсюда берутся id для всего
остального.

## 8. Пример: запись — весь протокол целиком

Записи идут в два приёма. Ниже настоящая сессия, от вопроса до отказа.

**Шаг 1 — модель проверяет, ничего не записывая.** Инструменты записи
по умолчанию делают сухой прогон:

```
> отметь на DEMO-0001 сервисное обслуживание, замена вентилятора
  → search_inventory({"query": "DEMO-0001"})
    success
  → record_item_event({"item_id": 1, "event_type": "service", "notes": "замена вентилятора"})
    success

Status: success
Action: search_inventory [success] → record_item_event [success]
Data: Проверка прошла успешно. Сервисное обслуживание с комментарием
«замена вентилятора» можно записать на изделие DEMO-0001 (id=1).
Подтверждаете?
```

Сухой прогон — не заглушка: трекер выполняет **все настоящие проверки**
в настоящей транзакции и откатывает её. Если правило процесса не
позволяет этот этап, ошибка придёт здесь, до всякой записи.

**Шаг 2 — вы соглашаетесь, и агент останавливается ещё раз:**

```
> да
  → record_item_event({"item_id": 1, "event_type": "service", "notes": "замена вентилятора", "dry_run": false})

  ⚠ Модель хочет записать в базу: record_item_event({"item_id": 1, "event_type": "service", "notes": "замена вентилятора"})
    Выполнить? [y/N] n
    error — refused_by_user

Status: success
Action: record_item_event [error — refused_by_user]
Data: Запись отменена — пользователь не подтвердил. Ничего не записано.
Errors: record_item_event: refused_by_user
```

Это не дублирование. Первый вопрос задала **модель** — её можно
уговорить, обмануть или она может просто забыть спросить. Второй задал
**код**, который выполняет вызов; его нельзя ни забыть, ни обойти
формулировкой. Ни один коммит не уходит в трекер без явного `y` в этой
строке.

Ответили `n` — в этом ходе больше не спросят. Иначе модель, которая
проигнорировала отказ, дёргала бы человека до упора.

## 9. Как читать ответ

Формат один и тот же везде — и внутри, между инструментом и моделью, и
снаружи, между агентом и вами:

```
Status: success | error
Action: <что делали>
Data:   <ответ>
Errors: <код: сообщение + подсказка>
```

- **`Status`** относится к **ходу**, а не к вызовам внутри него. В
  примере выше `success` при отказанной записи — не опечатка: агент
  корректно сделал своё дело и внятно сообщил, что записи не было.
- **`Action`** — цепочка вызовов с исходом каждого. По ней видно, что
  агент реально сделал, а не что он про это рассказал.
- **`Errors`** заполняется и при `Status: success`, если по дороге
  что-то падало. «Ответил, но только после трёх отклонённых вызовов»
  стоит знать, иначе это невидимо.

**Сверяйте `Data` с `Action`.** Модель — единственное звено, которое
может сказать неправду; трасса не может. Если в `Data` написано
«записал», а в `Action` нет вызова с успехом — верна трасса.

## 10. Если что-то не работает

Первые четыре — про токен, лечатся разделом 4.

| Что видно | Что это значит |
|---|---|
| `no_token_configured` | не задан `SERVER_TRACKER_TOKEN` — запрос даже не отправлялся |
| `api_disabled` | не выпущено ни одного живого токена (или последний отозвали); выпустить на `/api-tokens` |
| `unauthenticated` | токен неверный или отозван. Восстановить нельзя — выпускай новый |
| `forbidden` | роль не позволяет: `viewer` там, где нужна запись, — либо пользователя токена понизили, и токен урезался вместе с ним |
| `service_account_disabled` | пользователя токена деактивировали; активировать на его карточке в `/users` |
| `transport_error` | трекер не отвечает: не поднят, или `SERVER_TRACKER_URL` не тот |
| `prerequisite_not_met` | правило процесса: этап нельзя записать в этом порядке. Не поломка, а отказ по существу — сообщение объясняет, чего не хватает |
| `components_locked` | изделие укомплектовано, состав закрыт; открыть — событием `disassembled` |
| `invalid_arguments` | модель передала не тот тип. Обычно исправляется сама на следующем шаге |
| `repeated_call` | модель повторяет один и тот же неверный вызов. Агент сдался вслух — переформулируйте или сделайте это в вебе |
| `step_limit` | 12 шагов без ответа, скорее всего зациклилась на одной ошибке |

**Ошибка в инструментах или в модели?** Запустите `demo.py`. Он ходит в
трекер теми же функциями, без LLM. Работает — значит дело в модели или
формулировке; не работает — в токене, адресе или самом трекере.

**Длинный разговор начал путаться.** История диалога не подрезается; в
контекст 32768 несколько `get_item` по укомплектованному изделию
вытесняют начало разговора. Перезапустите `chat.py`.

## 11. Что стоит и не стоит спрашивать

Хорошо ложится:

- «где стоит эта деталь», «где она стояла раньше» — разбор отказов и РМА;
- «что с этим изделием», «всё ли укомплектовано»;
- «что сейчас в тестировании», «сколько отгружено»;
- «что должно быть в этой машине по конструктору»;
- «отметь этап», «поставь деталь», «сними деталь» — с подтверждением;
- замена детали — агент снимет старую и поставит новую, но подтверждать
  вы будете **дважды**, по разу на каждую запись. Серийник новой детали
  назовите сразу: без него агент переспросит, и правильно сделает.

Плохо ложится:

- всё, чего нет среди девяти инструментов: пользователи, токены, файлы,
  прошивки и MAC (в API они есть, инструментов пока нет);
- массовые операции — цикл ограничен 12 шагами;
- вопросы к аналитике по всей базе: агент видит ровно то, что отдают
  девять вызовов, он не выполняет SQL.

Формулируйте по одному действию за раз. «Проверь и, если всё хорошо,
отгрузи» модель выполнит, но подтверждать вы будете вслепую.

## 12. Переключение на внешнюю модель

```bash
.venv/bin/pip install langchain-anthropic
export MODEL_PROVIDER=anthropic ANTHROPIC_API_KEY=...
.venv/bin/python chat.py
```

Меняется только левая стрелка на схеме. Инструменты, промпт, цикл,
предохранители и токен — те же самые: про провайдера знает единственный
файл `model.py`.

Учтите, что переезжает проводка, а не поведение. Локальная модель
ошибается чаще, поэтому отлаживать разумно на ней: промпт, написанный
под слабую, на сильной окажется просто избыточным, а обратное — нет.
